> 目的: 網羅データ(684 OB career / 記録室 / 全史ランキング / 今季split)を **記事(post+X)に変換**する

## 0. 方針(再掲・1行)

サイト=ストック(参照ページ・指名検索)、**記事=フロー(話題・X拡散・鮮度)= 本ミッション**。
記事は既存 `data-insight` エンジン(allow/disallow・閾値・タイトル4case・dedup・eyecatch・主語巨人)を**流用・拡張**し、再発明しない。

## 1. 既存エンジンの遵守事項(全新タイプ共通)

- **タイトル**: `【巨人データ】…` / 12–60字 / 末尾 `…` 禁止 / 同 event 重複禁止 / 主語=巨人選手のみ。
- **dedup**: 同 subject+metric は cooldown 7日、再掲は 5%変化 or 順位band([1,5,10,30])超え。
- **eyecatch**: ①元記事 → ②`player_eyecatch_map.json`(67名)→ ③巨人マーク `63578`。
- **品質ゲート(CLAUDE.md §9/§16)**: 時系列 / title-body mismatch / 1記事1核 / thin body / AI tone / 公式X不足。
- **Voice**: ヨシラバーVoice(数字根拠・辛口必須・読み・巨人愛着地、優等生締め NG)。
- **X 自動投稿**: 既存(postgame/lineup)は常時。**新タイプの X 解放は §11 user 判断**(新カテゴリ)。サイト publish は自律。
- **誇張しない**: 公式 WAR/UZR/球速等の有料feedは出さない。簡易指標は明記。

## 2. 新記事タイプ 詳細設計

### ② 節目カウントダウン / 達成

| 項目 | 設計 |
|---|---|
| 目的 | 名球会・通算記録への接近を「あと○」で煽る。ファン価値最大・低コスト。 |
| ペルソナ | P1(コア)+ P3(ライト)。X拡散向き。 |
| トリガ | 現役選手の通算が節目に接近: 安打2000 / 本塁打500・400 / 勝利200 / セーブ250 等まで **残り ≤ 30(打撃)/ ≤ 10(投手)**。`compute_career_milestones` 既存。 |
| データ源 | NPB career cache(467、現役通算)。 |
| タイトル | case C 拡張: `【巨人データ】{player} 通算{stat}{value}、{milestone}まであと{n}`<br>例: `【巨人データ】坂本勇人 通算1985安打、2000安打まであと15` |
| 本文構造 | ①リード(あと○・到達ペース予測)→ ②直近の通算推移(月別/今季ペース)→ ③節目の意味(名球会等)→ ④出典 → ⑤`/data/{player}` 内部リンク。 |
| dedup | 同 player+milestone は残り数が変化した時のみ再掲(cooldown 7日 + 残り≥1減)。達成記事は **1回限り**(達成フラグ)。 |
| X | 接近は X 候補、**達成記事は速報級**(user 解放後は postgame 並み優先)。 |

### ③ 今日は何の日(OB) ★684 OB データが最も活きる

| 項目 | 設計 |
|---|---|
| 目的 | OB の「○年前の今日」を毎日 1–3 本。P2(歴史層)直撃・SEO(`巨人 今日は何の日`)・低コスト・**毎日確実に弾がある**。 |
| ペルソナ | P2(歴史・レジェンド層)中心 + P1。 |
| トリガ | 当日(JST)に一致する OB の出来事: デビュー / 引退 / 記録達成 / 誕生日 / 名場面。`ob_legends_full.json`(684、years)+ 拡張 `config/ob_anniversary.json`(節目イベント、半静的)。 |
| データ源 | 684 OB career + years(今回構築)。日付付きイベントは段階拡充(まず誕生日・デビュー年から、固定表で記録達成日を追加)。 |
| タイトル | 新 case E: `【巨人データ】{n}年前の今日、{player}が{event}`<br>例: `【巨人データ】46年前の今日、王貞治が通算800号本塁打` |
| 本文構造 | ①リード(何年前・誰が何を)→ ②当時の文脈(その年の成績/順位)→ ③通算での位置づけ → ④出典(Wikipedia等)→ ⑤`/data/{player}` 内部リンク。 |
| dedup | 同 player+event は **1年に1回**(命日/誕生日は毎年OK、同日重複のみ禁止)。1日の本数上限(例 3本)で thin 乱発防止。 |
| eyecatch | OB は写真少 → ②map(67名)該当時のみ写真、他は巨人マーク。 |
| X | 歴史枠は拡散弱め → 当面サイト publish のみ、X は user 判断。 |
| 段階 | Phase1=誕生日+デビュー年(years から自動)→ Phase2=記録達成日(固定表 `ob_anniversary.json`)。 |

### ④ 通算ランキング変動(現役 × 全史)

| 項目 | 設計 |
|---|---|
| 目的 | 現役が球団/NPB 歴代通算ランキングで順位を上げた瞬間を記事化。「歴史に追いつく」物語。 |
| ペルソナ | P1 + P2(現役と歴史の接続点)。 |
| トリガ | 現役通算が、全OB横断ランキングで **誰かを抜いた / band([10,20,50,100])を超えた**。前日スナップショットと比較。 |
| データ源 | NPB career(現役)+ `ob_legends_full.json`(全OB横断)= 今回の網羅で初めて可能。 |
| タイトル | case C 拡張: `【巨人データ】{player} 球団通算{stat}{value}、歴代{rank}位に浮上({抜いた相手})`<br>例: `【巨人データ】岡本和真 球団通算248本、歴代9位に浮上(中畑清を抜く)` |
| 本文構造 | ①リード(浮上・抜いた相手)→ ②上位の顔ぶれ(歴代TOP10)→ ③このペースでの到達見込み → ④出典 → ⑤`/data/record` + `/data/{player}` 内部リンク。 |
| dedup | 同 player+stat は順位が動いた時のみ(cooldown 7日 + rank 改善)。 |
| X | 「歴代○位浮上」は拡散向き → user 解放後は優先。 |

### ⑤ ホット&コールド(直近トレンド)

| 項目 | 設計 |
|---|---|
| 目的 | 直近 N 試合の急上昇/急降下を可視化。「今誰が乗ってるか」需要。既存 data-insight の延長。 |
| トリガ | 直近5/10試合の打率・OPS・防御率が、シーズン平均から **閾値(例 ±0.080 打率 / ±1.50 防御率)** 乖離。 |
| データ源 | insight.db(今季 logs、既存)。 |
| タイトル | case A: `【巨人データ】{player} 直近{N}試合 打率{value}、絶好調({scope})`(disallow 指標は使わない) |
| 本文構造 | ①リード(誰がどれだけ)→ ②直近 vs シーズンの対比表 → ③要因の数字(本拠/対左右等の既存split)→ ④`/data/{player}` 内部リンク。 |
| dedup | 既存 dedup(7日 cooldown + 5%変化)。 |
| X | postgame 級ではないが好調系は拡散向き、段階解放。 |

### ⑥ 現役 vs レジェンド対比(物語)

| 項目 | 設計 |
|---|---|
| 目的 | 「同年齢/同試合数時点で、現役は歴代レジェンドと比べてどうか」。P2×P1 を繋ぐ読み物。差別化度高。 |
| トリガ | 現役主力が、あるレジェンドの「同年齢時通算」を上回った/迫った時。 |
| データ源 | NPB career(現役)+ `ob_legends_full.json` 年度別(OB)。**年度別データが要る**ため OB career 拡充が前提。 |
| タイトル | 新 case F: `【巨人データ】{age}歳時点、{player}は{legend}を超えるか(通算{stat}比較)`<br>例: `【巨人データ】27歳時点、岡本和真の通算本塁打は松井秀喜に並ぶ` |
| 本文構造 | ①リード(誰 vs 誰・どの軸)→ ②同年齢時点の対比表 → ③この先の見通し(辛口)→ ④出典 → ⑤両者 `/data/` 内部リンク。 |
| dedup | 同 player+legend+軸 は cooldown 長め(14日)。乱発しない(物語性が薄まる)。 |
| X | 物語系は拡散向き、ただし精度要(事実誤認NG)→ 品質ゲート厳格 + user 解放判断。 |
| 注意 | OB 年度別の精度が肝。今回 scraper は通算は検証済だが、年度別の age 計算は生年月日が要る → profile 拡充が前提(Phase2)。 |

## 5. 段階ロードマップ(記事側)

1. **継続監査ループ再起動(§16)** — 既存データ記事の fail pattern 集計 → 共通の崩れ特定 → 改善起票(本文品質=最優先)。
2. **③ 今日は何の日(OB)Phase1** — 誕生日+デビュー年(years から自動)で日次 1–3 本。684 OB が即活きる、毎日弾がある、低コスト。
3. **② 節目カウントダウン** — `compute_career_milestones` を記事 trigger に接続。
4. **④ 通算ランキング変動** — 全OB横断ランキング + 前日 snapshot。
5. **⑤ ホット&コールド** → **⑥ 対比**(profile/年度別精度を見て)。

## 6. 正直な境界

- ③ の「記録達成日」は固定表 `ob_anniversary.json` の整備が必要(誕生日/デビュー年は years から即)。
- ⑥ は OB の生年月日・年度別精度が前提(未検証 → Phase2 で検証してから)。
- 新タイプの **X 自動投稿は全て §11 user 解放判断**。最初はサイト publish のみで品質を見る。
- 量より先に質(thin/AI tone/事実誤認の品質ゲートを全タイプ通す)。

### 7.4 クリティカルパス / 推奨実装順

**原則**: ①依存ゼロ×高ROI を先に → ②共有部品(全史ランキング)を作って2用途同時回収 → ③要検証(⑥)は後。

| Phase | 内容 | 理由 |
|---|---|---|
| **Phase 0(即・並行)** | **§16 継続監査** + **③ 今日は何の日 Phase1** | 依存ゼロ・最高ROI。§16=本文品質(最優先)、③=毎日弾が出る新コンテンツで684 OB を即収益化(SEO/P2)。 |
| **Phase 1** | **② 節目** → **全史ランキング計算**(共有)→ それを使い **/data/ranking 通算タブ** と **④ ランキング変動記事** を同時 | ②は素材済で軽い。全史ランキングは1度作ればサイト+記事の2用途を回収=最も効率的な投資点。 |
| **Phase 2** | **/data/record 記録室ハブ** + **⑤ ホット&コールド** | 記録室はライバル最大moat(career+固定表)。⑤はengine延長で軽い。 |
| **Phase 3** | **⑥ 現役 vs レジェンド対比** | 年度別+生年月日の精度検証(scraper Phase2)が前提。物語性高いが事実誤認NGのため最後。 |

### 7.5 推奨スタート(1点)

> **Phase 0 を並行で開始。先頭の単独着手なら『§16 継続監査ループ再起動』。**
> 理由: (1)CLAUDE.md の最優先が本文品質(§9/§16)、(2)依存ゼロで即着手、(3)既存記事の崩れを直さないまま新タイプ(③)を量産すると同じ崩れを増殖させるため、**品質の土台を先に固める**のが正しい順。
> ③ 今日は何の日 は品質軸を確認しつつ並行 or 直後に着手。
