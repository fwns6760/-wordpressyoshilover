## 0. 勝ち筋(一行)

> **巨人選手の網羅(現役 + 全OB・レジェンドの career・記録・ランキング)では正面から戦い追い越す。**
> **戦わないのは他11球団 / 侍ジャパン / MLB / 過去の試合単位ログ だけ。**
> **その上で、モバイル / 分析 / 実写真 / 鮮度 / 到達予測 / 共有 の「密度」で圧勝する。**

「巨人 個人データ No.1」という看板の category は**まさに巨人選手そのもの**。
そのカテゴリで No.1 を名乗るには、**実体(=巨人選手)の網羅が前提(table stakes)**であり、密度はその上の差別化。
→ **量と密度は二択ではなく、両方とも必須**。当初の「総量で戦わない/密度だけで勝つ」は誤り(現状 OB 21人では「今季深掘り No.1」止まりで、看板の No.1 は取れない)。

KPI は二本立て: **(1) 巨人選手の網羅率(対ライバル掲載選手)** と **(2) 選手1ページの密度・使い勝手**。

## 0.6. 選手網羅のターゲット定義(user 確定 2026-06-03)

- **巨人選手の網羅ターゲット = `my-favorite-giants.net` に掲載されている巨人選手の全集合**。
- ライバルに居る巨人軍・レジェンド選手は**全員カバーする**(現役 + OB すべて)。

## 2. 自社素材の現実(repo grep で verify)

- **現役 career**: `npb_career.json`(467 / GCS 日次 ingest、現巨人ロスター全員の年度別+通算+プロフィール+ドラフト)。`compute_career_milestones` / `_build_career_milestones_html` 既存。
- **OB career**: `config/ob_career_yearly.json`(**現状 21人のみ**: 長嶋/王/川上/原/高橋由伸/松井秀喜… 年度別)。→ **ライバル掲載の全巨人OBへ拡張するのが本設計の最重要タスク**(§0.6)。
- **career scraper**: `npb_career_scraper.fetch_player_career(npb_id)` = **ID 1個で年度別+通算+プロフィールを NPB 公式から取得**。467 が現役ロスターで日次運用中。OB へは「ID 名簿 + 一度の bulk scrape」で拡張可能(試合単位 backfill ではない=安い)。
- **今季**: `insight.db`(games / batting・pitching_logs、2026今季のみ)。打順別/球場別/対球団/序中終盤/曜日/月/交流戦/RISP/対左右/セイバー16(456/457/461)。
- **鮮度**: 毎日更新。セ順位表・日程・予告先発(NPB scrape、459)。
- **持っていない**: 過去の「試合単位」history、守備指標、順位の多年 history。

→ **記録室・タイトル・OB網羅は「career(通算/年度別)」由来なら作れる。「試合単位 history」由来なら作れない。** この線引きが全 Tier 判断の軸。
→ ★重要修正: 「**全OB career 網羅**」は career ページ scrape の反復であり、**安い(Tier 1)**。当初これを「試合単位 backfill」と混同して Tier 3(降りる)に誤分類していた。**降りない。No.1 の本命タスク**。

## 6. Tier 別 構築順(rival-parity 468 と整合・改定後)

0. **🟢 Tier 0 = No.1 の土台(網羅)**: **全巨人OB career bulk scrape**(現役は467済 / OB 21人 → ライバル掲載の全巨人選手へ)。ID 名簿作成 → 一度の bulk scrape → `/data/legends` と選手ページに全選手展開。**これが「巨人個人データ No.1」の前提**。
1. **🟢 Tier 1(career/固定表で即)**: `/data/record` 記録室ハブ(468-9)→ 名球会カウントダウン(468-10)→ 殿堂(468-11)→ 球団変遷/本拠地比較(468-13)→ 選手ページに career年度別+マイルストーン露出。※ Tier 0 が進むほど記録室・ランキングの厚みが「全史」化する。
2. **🟢 ランキング拡充**: OPS/SLG/OBP/WHIP/K-BB(E)。全OB網羅後に「歴代通算ランキング(全史)」へ。
3. **🟢 サイドバー / グローバルナビ**(§9、user 要望): /data 全ページに分かりやすい固定サイドバーを付ける。
4. **🟡 Tier 2(scrape設計)**: `/data/title` タイトル年度別(468-12)→ `/data/roster` 故障者IL/FA/トレード(468-14/15)→ ドラフト(468-2)。

**最初の1機能(推奨)**: 量と密度どちらを先に体感させるかで2案。

- (b) **moat 奪取先行**: `/data/record` 記録室ハブ → ライバル最大moatに最小コストで並ぶ(密度の体感が早い)。
- → **推奨は (a)**。看板「No.1」の前提が網羅であり、記録室・ランキングも網羅が進むほど価値が上がる(土台が先)。

## 9. SEO・収益化(user 最重要: 稼ぎたい / 2026-06-03)

> user 方針:「**網羅性と SEO**。稼ぎたいから」。→ 収益エンジン = **検索流入 → 広告(AdSense)**。網羅性はその燃料。

**実機検証(2026-06-03、yoshilover.com で実取得):**

- ✅ `/data/` は **noindex なし / robots.txt 許可** = **indexable**(旧メモリ「noindex前提」は /data に非該当)。
- ✅ 選手ページに **canonical + 構造化データ(application/ld+json ×3)+ OGP(×7)** 完備。
- ✅ **page-sitemap.xml に /data URL 120件**収録済(クロール導線あり)。
- → 技術土台は既にある。**残る伸びしろは「網羅(=ページ数)」と「各ページの質」**。

**SEO 戦略 = 網羅と直結(これが (a) 網羅先行を推す最大の理由):**

1. **ロングテール面の拡大**: 全巨人OB を選手ページ化 = **数百の indexable ページ追加**。各ページが「`<選手名> 通算成績 / 年度別 / 成績`」検索を取りに行く。網羅率↑ = 検索面↑ = 流入↑ = 収益↑。
2. **per-page 最適化**(既存 title ルール / SEO SIMPLE PACK 挙動と整合):
   - title = クリックされ検索語を含む形(例:`坂本勇人 通算成績・年度別【読売ジャイアンツ】`)。
   - 本文先頭に lead 文(SEO SIMPLE PACK は og:description を本文先頭から生成 → lead 必須)。
   - featured image を選手別に(`player_eyecatch_map` / OGP カード差別化)。
3. **回遊性 = 滞在/クロール深度**: §8 サイドバー + 関連選手リンクで内部リンクを厚く(直帰率↓ = 広告 viewability↑、クロール網羅↑)。
4. **鮮度シグナル**: dateModified + 「最終更新 ○○ 現在」可視化。毎日更新はライバルが偏る所、Google の fresh 評価で差。
5. **sitemap 自動収録**: 新規選手ページを page-sitemap に自動追加(取りこぼし防止)。
6. **thin/duplicate 回避**: データの薄い OB はテンプレ羅列だけだと thin page 判定リスク → 最低限の固有文(通算ハイライト lead)を入れる min content gate。

**収益の現実(誇張しない):** AdSense 単価×PV。データページは検索意図が明確で PV が積み上がりやすいが、収益化は「**indexable ページ数 × 検索順位 × 滞在**」の総合。網羅(量)→ SEO(面)→ 回遊(質)→ 広告、の順で効く。
