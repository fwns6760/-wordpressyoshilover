## 3. 目標サイト IA(巨人特化)

```
/data/ (cluster: 全選手ハブ)
  ├─ /data/<player>/  選手ページ(本丸 = SEO ロングテール)
  │     季別成績 / 直近 / 打順別 / 球場別 / 対球団 / 序中終盤
  │     ★追加: 曜日別 / 月別 / 交流戦vsリーグ戦 / 試合別ログ (Phase B)
  │     投手: 前回登板 / season / (救援)防御率
  │     構造化(SportsPlayer)+ 関連選手 + 関連記事 + dateModified
  ├─ /data/team/      チーム成績(打率/防御率の球団内・セ内ランキング)★新規B
  ├─ /data/schedule/  日程・結果カレンダー(games から)★新規B
  ├─ /data/lineup/    スタメン履歴 / 先発ローテ(lineups/pitching_logs)★新規B
  ├─ /data/roster/    公示・登録抹移・負傷(記事テキスト由来、出典明記)△半B
  ├─ /data/legends/   ★OB・レジェンド hub(老ファン向け、既存OB21名を束ねる)
  └─ /data/ranking/   歴代/通算ランキング ← 多年データ前提 = Phase C
```

> 対象読者は「コア巨人ファン + データ好き」に加え **老ファン(OB・歴史 needs)** を明確な柱に置く(§8 OB)。

## 7. UI/UX 設計(ベンチ深掘り分析ベース、2026-06-01 WebFetch)

### 7.1 ベンチ2サイトの UI/UX 実態(verified)

| 観点 | baseballdata.jp | my-favorite-giants.net |
|---|---|---|
| 思想 | PC向けデータ分析ツール | 体系的データベース(20年運用) |
| 表 | 30-40行×20+列の超高密度、横スクロール必須 | テーブル羅列、余白なし |
| ナビ | チームID構造 `/c/1/`(巨人)、年度 `/YYYY/`、☰折りたたみ | 大分類8+中分類50+、■□で更新可視化 |
| URL | セマンティック(予測可能) | セマンティック `/giants_data/種/詳細/年.htm` |
| モバイル | **見づらい(横スクロール)** | **レスポンシブ弱** |
| ビジュアル | テキスト簡潔・装飾最小・青リンク | **2000年代グレー基調・視認困難** |
| 弱点共通 | 情報密度過多 / 余白なし / スクロール疲労 / モダンさ無し | 同左 |

### 7.2 勝機(両者の穴)と我々の UI/UX 原則

**穴 = モバイル・モダンさ・見やすさ**。ここで差別化する。

1. **モバイルファースト**: 両ベンチの最大の穴。スマホで横スクロール不要。重要数字は大きいカード、詳細表は折りたたみ/タブ/スワイプ。
2. **要約 → 詳細の段階表示**: 20+列を一度に出さない。各ページは「目立つ KPI 数枚(打率/HR/直近) → 詳しい split は展開」。情報密度は出すが疲れさせない。
3. **モダンな見た目 + ブランド**: グレー羅列でなく、ヨシラバーのブランド(橙系)+ 余白 + カード + 読みやすい数字フォント。ダークモード考慮。
4. **鮮度の可視化(彼らの ■□ の現代版)**: 「最終更新 ○分前」「今の調子↑」バッジ。鮮度は我々の強み([[project_site_direction_data_focus]])。
5. **セマンティックURL + 多軸ナビ(SEO=学ぶ)**: `/data/<player>/`(済)に加え `/data/team/` `/data/schedule/` `/data/<player>/splits` 等を予測可能・パンくず・関連リンクで網に。
6. **構造化データ + リッチリザルト**: 既存 JSON-LD(SportsPlayer 等)を表に対応させ、Google で表/評価が出る形へ。

### 7.3 ページ別 UI 方針(本丸=選手ページ)

- **選手ページ `/data/<player>/`**: 上から
  1. ヒーロー: 写真 + 名前 + 背番号/守備 + **今の調子バッジ**(直近成績/連続)
  2. 主要 KPI カード(打者: 打率/HR/打点/OPS、投手: 防御率/K/前回登板)= 大きく
  3. タブ or 折りたたみ: 季別 / 直近 / 状況別(打順/球場/対球団/序中終盤/曜日/月/交流戦)/ 試合別ログ
  4. 関連選手 + 関連記事 + cluster 戻り
- **cluster `/data/`**: ポジション別グリッド(モバイルで崩れないカード)、検索/絞り込み。
- **team / schedule / lineup**: 表は段階表示(要約→詳細)、モバイルで縦に流れる。

### 7.4 「最初にこけない」ための設計順(UI/UX 起点)

1. **先に選手ページの UI/UX を刷新**(モバイル+段階表示+鮮度バッジ)= ベンチに対する差が一番出る面。データは既存のまま見せ方を勝たせる。
2. その器に Phase B の新 split を流し込む(器が良ければ追加が映える)。
3. team/schedule/lineup を同じ UI 言語で増設。
4. SEO 技術(dateModified/構造化/内部リンク)を全ページ共通で。

→ **データ網羅(Phase C)より先に「見やすさ」で土台を勝たせる**のが、最初にこけない順序。
